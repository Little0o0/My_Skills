# Application Goal：在用户指定领域中实现有实质价值的理论成果转化

## 0. 协议身份、来源与优先级

- **协议 ID**：`theory-to-application-goal`；**版本**：`2026-09-29.3`。
- **中文规范**：`application_goal_zh.md`；**英文执行入口**：`application_goal.md`。两份文件必须语义一致、章节对应、同步更新；不一致时以中文规范和用户最新指示修订英文，不利用差异放宽验收条件。
- `MUST / MUST NOT` 表示必须／禁止，`SHOULD` 表示默认应执行、偏离须说明，`MAY` 表示允许。系统／开发者／运行器约束优先，其次是用户最新指示，再次是本协议。
- **流程来源不是成果来源**：`idea_goal.md` 是理论研究流程规范，`idea_goal_zh.md` 是其中文对应；它们本身不是待应用的数学定理。实际理论成果从用户指定的论文／定理／证明文件加载；本项目可将 `idea.md` 与其引用的冻结证明作为候选来源，但必须核验实际内容和版本，不自动继承旧的“已完成／已验证”标签。
- 本协议重点继承 `idea_goal.md` 的问题卡、原始文献核查、先价值后验证、独立跨模型评审、证据等级、无限轮次、检查点和防死锁机制。**有意替换其“暂不考虑下游落地”的目标**：本协议以指定领域中的应用影响与论文级贡献为目标，使用 §2 的应用成功标准；不机械要求每项应用必须产生新数学指数，也不把小幅常数优化自动视作突破。
- 在应用运行中，目标、状态文件、阶段和恢复顺序以本协议为准；`idea_goal.md` 的其余被引用方法不能覆盖这些应用专用条款。记录来源协议的版本与哈希；将来来源协议变化时显式评估差异，不静默改变正在运行的目标。
- **制作、翻译或 review 本协议不启动应用研究，也不重启已完成的理论 goal。** 只有用户明确启动／恢复，或应用 goal 运行器指示继续时，才进入研究循环。本次若仅要求文档，则只生成文档与其 review。

## 1. 用户输入与研究启动边界

### 1.1 必需输入与可自主补齐项

实际启动前必须确定：

1. **用户指定的下游领域及允许范围**，例如某类数据库查询、某类 GPU 图算子、某类数据质量任务。示例不是默认领域。不得替用户从候选示例中选定领域。
2. **理论来源**：用户指定的成果及其依赖；若未指定且本目录只有明确的候选成果，可检查 `idea.md` 并登记暂定来源，有多份实质不同成果或不明确时提出简短澄清。
3. **执行授权**：用户明确启动本应用研究，或收到对应应用运行器的继续指示。已有理论研究的完成记录不构成新的应用启动授权。

实际启动请求中，领域缺失、理论来源不明确或执行授权缺失时，状态记为 `WAITING_INPUT`；一次简短询问集中说明所有阻止启动的必需澄清，不为可自主补齐项反复追问。可以完成获准的协议／资料整理，不能自行开展某领域实验。纯文档制作请求不需要为了占位字段追问领域，也不建立应用运行。`WAITING_INPUT` 是本地工作流状态，不是擅自修改 goal 运行器的阻塞状态。不要为可自主填写的参数逐项要求用户审批。

用户可以额外指定任务、排除项、目标会议、硬件／数据、质量容差、指标、预算或隐私限制。缺省时：论文 venue 不是前置条件；不得编造硬件／数据授权；其余细节通过领域侦察形成问题卡，公开说明假设。资源未授权的部分不执行，仍可做可用资料范围内的分析。

### 1.2 启动配置模板

收到实际应用启动请求后，在 `applications/<run-id>/RUN_CONFIG.json` 保存类似以下的合法 JSON；这是数据模板，不是自动完成校验的 JSON Schema。此模板中的 `null` 表示未填写，不是 0、无限资源或已获许可；`false` 不会自行变成 `true`。

```json
  "protocol_version": "2026-09-29.3",
  "run_id": null,
  "user_domain": null,
  "user_domain_evidence": null,
  "allowed_scope": null,
  "excluded_scope": [],
  "execution_authorized": false,
  "authorization_evidence": null,
  "theory_sources": [],
  "workflow_sources": [
    {
      "path": "application_goal.md",
      "version": null,
      "sha256": null
    },
    {
      "path": "idea_goal.md",
      "version": null,
      "sha256": null
    }
  ],
  "target_venues": [],
  "authorized_resources": {},
  "resource_limits": null,
  "quality_constraints": [],
  "success_profile": null,
  "status": "DRAFT"
}
```

主执行者根据真实用户指示填值并记录证据，不要求用户手工编辑 JSON。启动研究必须有非空领域、范围、来源和授权；字段不全不得标为已启动。`success_profile` 可以在初步侦察后确定，但必须在确认性实验前冻结。

`status` 只取 `DRAFT / WAITING_INPUT / ACTIVE / PAUSED / COMPLETE / STOPPED` 中一个值：草案、缺必需输入、已授权运行、用户／运行器暂停、验收通过、用户／运行器停止但未完成。`execution_authorized=false` 或必需输入未齐时不得写 `ACTIVE`；`COMPLETE` 仅在 §2.3 全部满足后使用；暂停／停止／恢复须依据真实用户／运行器指示，候选失败不能触发 `STOPPED`。这些是应用本地状态，不替代运行器的状态管理。待澄清的真实启动请求可保存 `DRAFT / WAITING_INPUT` 记录，不代表研究已启动；纯文档请求仍不创建运行目录。

`theory_sources` 的每个元素必须是含 `path`、`version`、`sha256` 的对象，可另加定理位置和证据路径。`workflow_sources` 用同样的来源对象；填写实际读取内容的 hash。来源尚未解析时保留空数组／null，不能假造哈希。收到明确恢复指令且输入、授权和资源满足时再转为 `ACTIVE`。

## 2. 应用目标与成功标准

### 2.1 主目标

在用户指定的领域和约束内，利用可核验的理论成果，产出至少一项**有真实任务需求、理论适配正确、具有应用层新颖性、可独立复现、带来实质影响的算法／数据结构／系统方法**，并整理成可送同行评审的论文材料。

必须建立可审查的完整链条：

`用户任务 → 真实瓶颈 → 理论条件与对象映射 → 新机制 → 完整算法／系统 → 可测或可证的收益 → 适用边界 → 论文贡献`

主目标不是“给定理换一个应用名称”，也不是“只要有论文草稿就算成功”。除用户另行指定，本协议的完成点是**达到 preregistered 应用成功标准并交付 submission-ready 材料**，不是实际被会议接收、上线生产或证明已有社会影响。实际投稿、外部发布和部署需要单独明确授权。

### 2.2 什么算实质进展

登记一个或多个适合领域的成功维度，并通过价值评审：

- **渐近进展**：同一问题与保证下改善端到端时间／空间复杂度，而非仅改善未成为瓶颈的中间计数界。
- **有机制依据的系统进展**：新算法或表示在公平资源／质量约束下稳定改善真实任务的时间、内存、能耗、成本或可处理规模，即使未改变渐近阶。必须超过测量噪声和低价值参数微调，阈值在验证前登记，不能靠更换硬件或降低质量冒充。
- **新能力或新权衡**：使原来资源预算内不可行的任务可行，或在重要质量—效率／精确性—空间权衡上达到新的可核验区域。

不设跨领域通用“2 倍”或“提升 5%”硬阈值。必须在 `APPLICATION_CARD.md` 中登记指标、方向、最小有意义改变量、任务规模区间、质量／资源约束、基线和判断方法；用户已有硬阈值不可自行降低。可先做小规模探索性测量辅助定阈值，但不得把已见结果的最小值倒填成成功门槛。

**不单独构成完成**：重新证明原定理、机械套用已有方法、仅换 GPU／模型／库版本、无端到端收益的局部指标、挑选有利数据切片、只有玩具例子、泛泛的落地清单、纯负面搜索日志、模型一致赞同、论文排版或 venue 匹配。

### 2.3 完成必须同时满足

1. 领域、任务、假设、输入分布／规模与保证满足用户范围及冻结问题卡。
2. 理论结论适用于实际任务，或所需适配／扩展已被完整验证；不得把未证桥接命题藏在实现中。
3. 存在非平凡的应用层机制或结果，相对于最新已核实且适用的强基线有明确增量。
4. 达到 preregistered 收益与质量条件，全部必要成本已计入；证据覆盖声明范围；若冻结的 `success_profile` 要求实现或实验，对应原型必须存在并复现关键结果（见 §10）。
5. 所有承重数学义务、程序正确性、实验可信性和新颖性义务已销账；没有核心 `UNKNOWN / UNREVIEWED`。
6. §9 要求的价值与验证跨模型评审已完成，重大异议由证据解决。
7. §10–§12 所列可复现材料、适用局限、完整推导和论文草稿均交付。

## 3. 无限循环、自主权限与停止

### 3.1 持续执行

- **轮次 K 无上限**：在已启动的应用研究中，持续到真正满足 §2.3 或用户明确停止；不承诺指定领域必然有可行突破或论文一定录用。
- 主执行者可在用户允许领域内自主选择子任务、构造候选、登记问题卡、改变机制、搁置失败候选和安排独立复核，不逐次请求“冻结批准”。
- **领域／用户硬约束不可自行变更**。域内换题可自主登记；换到域外、改用户质量要求、扩大花费／数据访问／生产权限必须取得明确授权。可以记录域外线索，但不能用域外成功代替本 goal。
- 每五轮或重大证据变化时汇报；汇报是通知，不因无回复而停止。每轮须有具体问题、动作、资源／批次结束条件和证据产物。
- 同一障碍连续两轮无有效进展时改变机制或暂缓该候选；连续三轮没有新可检验信息时，重新排序域内候选与瓶颈。减少重复小例子，不把重写计划当进展。
- 对一个候选的 `REJECT / INCOMPATIBLE / REFUTED` 不等于项目停止。多个失败也不证明整个领域无机会；若有覆盖明确范围的不可行性论证，只关闭该范围。
- 无限轮次不是无限费用；所有调用与实验受授权资源和预算约束。必要资源缺失且无其他安全工作时才报告真实阻塞，并遵守运行器的连续阻塞核验规则；不得仅因工作难、review 慢、上下文长或候选失败而置为 blocked。

### 3.2 调度与不死锁

- 先决定主执行者马上能做的关键路径工作，再分派独立、可并行、边界清晰的子任务。禁止委托唯一下一步后反复空等。
- 每个任务登记输入版本／哈希、负责人、工具句柄、读写范围、输出与结束条件；**同一文件同一时间只有一个写入者**。reviewer 只写自己的报告，不直接覆盖被审产物。
- 超时仅说明观察窗口结束；先核验同一句柄，不自动重启重复任务。变更或关闭任务后确认交接，再转移文件写入权。迟到产物保留为新版本，不覆盖当前证明或配置。
- 每轮记 `PROGRESS / VERIFIED_WAIT / NO_PROGRESS`。有效等待须有当轮可核验状态；只有等待意图、旧锁文件或未执行计划不能算有效等待或进展。
- 服务不可用、独立模型不足或局部缺证时，门禁保持关闭但其他工作继续；不要增加自设审批、无限仲裁或“等待用户认领候选”的锁。

## 4. 领域侦察与问题卡

### 4.1 从真实任务出发

先研究用户领域里的实际输入、输出、数据分布、质量要求、资源限制、更新频率、部署路径和现有实践。查阅原始论文、官方文档、公开代码、数据／工作负载来源和必要的领域资料；当前产品、算法库、venue 与 baseline 必须核验日期。

建立域内候选地图 `DOMAIN_MAP.md`：任务价值、已知解法、真实瓶颈、理论可利用结构、初步适配障碍、预期收益和最小判别动作。保留多个方向，深入一至两个；不要强求固定题数。需求假设没有现实证据时标为待验证，不伪造用户、部署或行业规模。

### 4.2 应用问题卡

每个深入候选建立版本化 `APPLICATION_CARD.md`，至少包括：

1. 用户领域、使用者与真实任务；输入／输出语义和排除范围。
2. 数据／工作负载来源、样本单位、规模参数、结构条件及其普遍性；训练、查询、构建、更新分开定义。
3. 硬件／系统栈、精度、并行度、动态性、失败模型、质量和安全约束。
4. 所用理论精确陈述、假设、参数、版本／哈希、证明与外部依赖状态。
5. 从任务到数学对象及回到输出的映射，新增假设、代价和未证义务。
6. 最强已核实适用基线、原理论给不了什么、拟新增机制、与普通工程优化的差别。
7. 可量化成功阈值、比较区间、统计／理论判断方法、质量底线、非目标与失败条件。
8. 风险、反例／边界测试计划、探索／确认数据切分、预期可复现材料。
9. 下一项能区分路线成败的工作；目标 venue 可空，后续按真实贡献定位。

探查阶段可有草案；进入确认性验证前，任务口径、阈值、数据处理规则及基线必须冻结。改变核心机制、语义、质量条件、工作负载或成功阈值，建立新版本、说明理由并重新评价值；旧结果不得迁移为新版本的盲测证据。

## 5. 理论到应用的适配审计

### 5.1 逐假设映射，不靠术语相似

在 `ADAPTATION.md` 建立“理论假设／结论—应用对象—证据—缺口—修复成本”矩阵。至少检查：

- 图／数据结构的方向、权重、平面性、连通性、稀疏性、动态性，或该理论实际要求的其他条件；不能因为都叫“图”“压缩”就声称适用。
- 输入规模、参数、位长和隐藏常数；连接扩充、细分、展开、离散化及索引可能把小参数变大。
- 结论究竟是存在性、计数、可构造算法、平均／最坏情况、精确／近似；不得把“状态数减少”直接写成“实际时间同比减少”。
- 编码、解码、输出恢复、tie、随机性与浮点误差；证明语义、可行域、误差与任务保证被保持。
- 桥接后的度量／损失／目标是否仍是应用真正关心的量；无向化、无权化、删边、近似不能无说明替换真实任务。

逐项使用 `SATISFIED / REQUIRES_PROOF / VIOLATED / UNKNOWN`。总体适配使用：

- `DIRECT`：现有假设与结论直接覆盖当前任务。
- `ADAPTED`：非平凡适配的语义／误差／成本已验证。
- `CONDITIONAL`：仍依赖明确未证的桥接或新增理论。
- `INCOMPATIBLE`：当前定义下有已证冲突／反例。
- `UNKNOWN`：信息不足。

在价值门前可用 `CONDITIONAL / UNKNOWN` 假设性评价潜在价值，不要求先完整证明；**最终成果验收必须达到与声明一致的 `DIRECT / ADAPTED`，不能以未证适配当完成**。

### 5.2 理论收益归因与必要性

必须回答“假如没有这个理论成果，我们是否也能得到同样的算法和结果？”区分：

1. 理论启发了新的算法／结构，直接改善可操作瓶颈；
2. 理论为原本启发式方法提供新的保证、适用范围或设计参数；
3. 只是把旧复杂度上界写得更紧，实际算法和能力完全未变；
4. 只是应用包装，与定理没有可检验关系。

前两者可以有价值，第三者须证明保证本身对领域有什么重要用途，第四者不能作为本 goal 的主成果。通过可行的消融、理论反事实、替代表示／解法或成本分解验证归因；不要求删掉定理文字就“运行消融”，也不以硬件提速代替理论贡献。

原成果如需新引理／扩展，登记为独立证明义务；仅借用 `idea_goal.md` §3.2、§6.2、§8.1–§8.2 的问题卡、改进、证明与验证方法，不引入其独立理论成果的成功标准或重新启动原理论 goal。此处“仅借用”限定桥接证明所采用的方法及独立理论成功／验收标准的排除，不影响 §0 与 §9.1 明示继承的流程与评审条款。桥接引理不必自己构成指数突破；来源协议的 `≥0.05` 本来只是选题启发式，不得把它变成桥接门槛。桥接引理按它对本应用候选的作用评价，应用价值与验收分别按本协议 §2、§6、§10；可以在域内推进，但不能退回无应用目标的无限纯数学研究。若理论来源出现缺口，依赖它的结论全部降级；可以修复或尝试域内其他适配，不自动重审每份无关历史材料。

## 6. 候选、阶段门与价值评判

### 6.1 阶段顺序

| 阶段 | 工作 | 通过条件／转移 |
|---|---|---|
| S0 输入与授权 | 确定领域、来源、范围与权限 | 缺必需输入则 `WAITING_INPUT`，否则 S1 |
| S1 侦察与轻量适配 | 查领域基线、实际瓶颈、列假设矩阵 | 形成具体候选；已冲突的路线归档或改写 |
| S2 候选与预登记 | 定量收益假设、新机制、风险与验证计划 | 足以让外部 reviewer 在“若成立”前提下评价 |
| S3 **价值／新颖性评判** | 重要性、适配潜力、增量、影响与可发表贡献 | `ADVANCE` 后才进入深入验证；其他按理由修订／暂缓／拒绝 |
| S4 **适配与正确性验证** | 补证映射、复杂度／误差账、成功档案要求时的原型与判别测试 | 正确性成立才进入正式性能／质量评测 |
| S5 确认性证据 | 实验型候选使用冻结配置、独立工作负载、公平强基线；理论型候选使用完整定理与可核验比较 | 按冻结成功档案达到阈值；实验不适用须事前登记并由 reviewer 确认，不可事后删去必需实验 |
| S6 独立验证与最终价值复评 | 审计证明／实现／评测／归因与当前查新 | 核心义务全过，重大变更回到 S3 |
| S7 论文与验收 | 完整材料、审稿视角、适用边界、§2.3 审计 | 实际满足才完成；否则继续最有信息价值的任务 |

轻量探针可以在 S1/S2 排除明显不匹配、估计参数或修复工具；它们不能替代价值门，不能变相提前做无边界的大规模优化。初步评审假定核心结论为真，讨论“是否值得做”；不以“未完成证明／实验”为唯一拒绝理由。

### 6.2 价值与影响力判定

对以下维度分别给 0–4 分和证据／理由，未知项记 `UNKNOWN` 而不是 0：真实任务重要性、适配可信入口、应用层新颖性、预期收益量级、公平比较与成本、覆盖范围／可复用性、可验证性、论文贡献清晰度。

分数只辅助排序，不表示正确率、录用概率或真实社会影响。给出明确分类：`ADVANCE / REWORK / DEFER / REJECT`。进入 S4 的候选必须完成所需外部价值评审且核心反对理由已处理；存在实质冲突不能靠投票强行通过。

价值 review 必须挑战：需求是否真实、条件是否过窄、是否已有更简单解法、构建成本是否吞掉收益、参数区间是否常见、改善是否只是改变硬件／质量／baseline，以及新定理究竟带来什么。负面结果是排除证据，不自动变成“应用突破”；若用户希望转为负面研究论文，需要显式重新定义目标。

## 7. 实现、实验设计与完整成本

### 7.1 先正确性，再性能

- 先用可核验的小例、边界例、已知反例和独立基准实现验证输出；核心正确性不成立时，性能结果不得作为成功证据。
- 对声称精确的方法，逐项证明语义保持并做差分测试；对近似／随机方法，登记误差、失败概率、对手／采样假设，并验证质量预算没有被隐性放松。
- 检查器也要测试：正确例、故意损坏例、维度／schema／数域校验；记录真实退出码。工具超时、空输出或启发式找不到解，不等于证明无解。
- 若成功档案要求原型，该原型必须实现承重机制而非调用隐藏 oracle；任何未计成本、手工预计算、不可获取索引都写入缺口。

### 7.2 成本与收益核算

按任务完整计入：数据取得／清洗、表示转换、预处理、索引构建、模型训练／调优、编译、CPU↔GPU 传输、内核启动与同步、存储、查询、解码／输出、动态更新／失效重建、重试与质量检查。没有某项成本时解释为何不适用，不预设所有任务都有 GPU。

若新方法预处理为 `P_new`、单次查询 `t_new`，基线为 `P_base`、`t_base`，必须比较

`T_new(Q) = P_new + Q*t_new` 与 `T_base(Q) = P_base + Q*t_base`。

只有 `t_new < t_base` 时才可按相应符号条件讨论摊销阈值；例如额外构建成本为正时，`Q > (P_new-P_base)/(t_base-t_new)` 才有总时间优势。计入实际更新频率和缓存生命周期。局部加速按端到端占比核算，输出本身的下界不能被压缩表示假装消除。

### 7.3 公平基线与实验覆盖

- 查最新已核实、**适用于同一任务和保证**的强算法／系统，而不是仅与原论文松上界或朴素实现比较；记录实现来源、版本、调优预算和不可用基线。
- 按声明固定硬件、精度、质量、资源预算、输入输出和工作负载；若资源不同，单独报告成本归一化，不能混入算法提速。
- 预登记数据来源、训练／验证／测试划分、采样单位、重复次数、随机种子、主要指标／阈值、排除规则、统计和停止方法。系统评测覆盖冷／热启动、批量、并发、峰值内存和规模变化中与声明有关的部分。
- GPU 时间使用可验证的同步计时；区分编译／预热、host 时间、device 时间与端到端时间。异步提交时间不等于执行时间；缓存收益、数据搬运不能只计在基线一边。
- 先使用开发集做探索，冻结后做确认测试。查看确认数据后改方法或阈值属于适应性选择，必须登记并采用新的独立确认数据或预登记的有效序贯／多重比较方法。无限循环不是无限窥视同一测试集。
- 根据声明报告效应量、方差／区间与运行波动；显著性不等于实际价值。确定性最坏界需证明，计时斜率拟合不能代替渐近证明。
- 使用代表性真实／现实约束工作负载与受控合成难例；分别说明代表性、许可证、可分享程度和规模覆盖。不允许从同一生成器大量抽样就声称覆盖整个领域。
- 保存负结果、退化区间和反例；做必要消融、敏感性与鲁棒性检查。若真实数据不可获得，证据限于受控环境，不得声称完成真实部署验证。

## 8. 新颖性、论文定位与交付

### 8.1 双重查新

同时查两条文献链：**原理论／相邻数学工具**，以及**目标领域已有索引、系统、算法和工程技巧**。同义术语、已有等价方法、专门针对子族的更强结果、公开代码和近期预印本都要检查。

在价值门前和最终声明前各做一轮。每条承重新颖性断言附原文位置／版本／检索日期；“未搜到”不等于“绝不存在”。将贡献区分为既有理论、已知适配、新桥接／新算法、新系统机制、新经验发现；原理论已发表或公开时正确归引，不重复计算创新量。

### 8.2 论文定位不是改名包装

venue 可由用户指定，也可在域内形成实质贡献后建议；不因为没有 venue 而阻塞研究。核实官方 scope、稿件类型、审稿要求、页数与截止日期，不凭旧记忆。数学定理、数据库索引、Web 问题、ML 能力、GPU 系统分别需要对应证据，不要求所有论文都做同样实验。

建立 `PAPER_CASE.md`：一句话任务、为什么重要、最接近工作、核心区别、技术难点、定理／算法／系统贡献、主结果、局限和最可能拒稿理由。以审稿人视角检查理论是否只是装饰、数据是否只为迎合假设、是否存在更强 baseline。不得许诺录用或把模型评分变成录用概率。

最终 `application.md` 与 `paper/` 至少包含精确问题、先前工作、假设映射、完整逐步推导／算法、复杂度和误差、按成功档案适用的实验方法与原始证据指针、适用的消融／反例／边界、贡献归属与参考文献。附录不能用来隐藏核心漏洞或在正文省略适配假设。

## 9. 评审角色、异构模型与审核门禁

### 9.1 继承的模型规则

按照 `idea_goal.md` §7.1–§7.4 执行，且本节作为应用协议中的操作摘要：

- 主模型保持 Codex 前端当前选择，不改全局默认。所有本机委托 agent 显式指定与主模型不同的底层模型；正式 reviewer 还须与其审核的关键产出生成模型不同。
- 同候选同阶段计入门禁的本机 reviewer 必须互异；新会话／别名／不同思考档位不构成异构模型。使用 `fork_context=false` 或实际等效的无继承上下文会话。
- 研究成果最低组合为**Claude 侧异构 reviewer + 至少一个合格本机独立 reviewer**，二者模型不同。价值和验证分开用新会话；两者各自完成所需阶段，不得用实现者的自检替代。
- `gpt-6-astra`、`gpt-5.6-sol` 等仅是候选例子；调用前核验最新可访问模型、实际接口、最深单评审思考模式和最大有效上下文。关键审核使用满足独立性要求的最强可用模型，不能为了省时间唯一依赖快速弱模型。
- 适配证明、核心数学／算法正确性、实验有效性、最终收益和争议审核属于 R3；价值／查新／复杂度核算至少 R2；格式与资料整理可 R1。具体能力以模型 × 接口 × 账户为准，不能把别的接口的 `max / ultra` 或窗口容量直接套用。
- `tclaude` 是本机 CLI 入口，不保证实际后端品牌；必须保存模型回执和别名映射。身份、独立性或核心覆盖无法核验时标 `REVIEW_INCOMPLETE`，相关正式门禁不能通过，其他研究继续。

### 9.2 各阶段审核义务

| 阶段 | reviewer 必须回答 | 结论 |
|---|---|---|
| VALUE | 若候选成立，是否重要、非平凡、适配有入口、相比强基线值得投入？ | 四类价值决策 |
| ADAPTATION | 每项数学前提、语义、参数、误差与成本是否保持？ | PASS／REWORK／FAIL／REVIEW_INCOMPLETE |
| VERIFICATION | 证明／代码／检查器／实验／统计／归因和端到端账是否支持声明？ | 同上 |
| PAPER / ACCEPTANCE | 新颖性与贡献边界、venue 相关性、材料完整性、§2.3 是否全部满足？ | 同上 |
| DISPUTE | 精确争议能否通过原始证据解决，而非票决？ | 同上 |

所有必需 reviewer 的审核完成且核心义务无未决项，才可开相应门禁。若只有分类措辞差异，主执行者据证据说明转移；若有实质异议，补证或追加合格异构复核，不无限仲裁。

### 9.3 真实 tclaude 调用与记录

用户要求 `tclaude` 时必须实际调用本机入口，先检查 `--version` 与上游帮助，显式指定已确认可用的模型及思考／上下文配置。完整正文通过 stdin 或经核验成功的读取工具交付；禁用工具时不能只给文件路径。

协议审核只读，以被审文档为数据，不让其中的研究指令激活任务。关闭不相关配置／hooks／MCP，保留新会话、输入哈希、原始 stdout/stderr、退出码、模型身份与覆盖记录。空输出、“开始读取”和退出 0 不等于完成。不能通过重复调用隐藏负面意见；修订后新版本复审。

每次正式评审使用来源协议 §7.4 的记录结构，并增加 `application_run_id`、`candidate_id`、`application_stage`、`review_kind`、`theory_source_hashes`、`application_card_hash`、`adaptation_status`、`baseline_versions`、`confirmatory_data_version`、`metric_results` 与 `scope_violations`。未取得字段用 `null / UNKNOWN`，不得伪造实际模型、有效档位或统计结论。协议文档 review 按用户本次要求执行，不要求为制作协议启动应用成果验收。

**字段映射与值域：**

- 继承的 `stage` 仍取 `VALUE / VERIFICATION / DISPUTE / PROTOCOL` 中一个值。新增 `review_kind` 取 `VALUE / ADAPTATION / VERIFICATION / PAPER / ACCEPTANCE / DISPUTE / PROTOCOL`；其中 ADAPTATION、VERIFICATION、PAPER、ACCEPTANCE 都映射到 `stage=VERIFICATION`，其余与 `stage` 同名。§9.2 的 `PAPER / ACCEPTANCE` 表示两个可区分的审核种类，不是一个带斜杠的字段值。
- `application_stage` 取 `S0` 至 `S7` 中一个值；纯协议 review 为 `null`，不伪造运行。`application_run_id`、`candidate_id` 在存在对应运行／候选时填真实标识，否则为 `null`。
- `adaptation_status` 取 §5.1 的 `DIRECT / ADAPTED / CONDITIONAL / INCOMPATIBLE / UNKNOWN` 中一个值；不是适配审核时未评估则为 `UNKNOWN`。`theory_source_hashes`、`baseline_versions` 是含实际路径／标识、版本／哈希的对象数组，未核实为 `null`。
- `application_card_hash`、`confirmatory_data_version` 是实际哈希／版本字符串，尚未取得为 `null`。理论型应用无确认数据时必须在问题卡解释不适用，不能用 `null` 假装实验已完成。
- `metric_results` 是对象数组，每项含 `metric`（字符串）、`unit`（字符串）、`baseline_value`、`new_value`（数值，或带证据位置的理论界对象）、`uncertainty`（区间／方差对象或 `null`）、`meets_registered_threshold`（布尔值或 `null`）和 `evidence_path`；后者两项缺失／未知不能通过收益门。未做收益核验时整个字段为 `null`，不能用空数组当作成功。
- `scope_violations` 是字符串数组；`[]` 表示已检查且未发现越界，`null` 表示未检查。非空数组表示存在越界，相关门禁不得通过，须先纠正范围或取得用户明确授权并登记新版本；新授权不追溯性抹除旧违规，受影响证据必须按新范围重验证。`null` 是核心未核项，不能支持最终验收。`VALUE` 使用四类价值决策；其他 `review_kind` 使用 `PASS / REWORK / FAIL / REVIEW_INCOMPLETE`。

这些值域必须由实际记录／校验器执行；数组允许多项，单值枚举只能选一项，不把 `|` 或 `/` 分隔的说明原样写入字段。是否满足最终验收仍看义务与证据，不由字段存在、空数组或单一 PASS 自动推定。

## 10. 证据等级与完成审计

- **实验支持**：有限数据、计时、抽样和经验规律；不证明全称结论、最坏复杂度或整个领域适配。
- **局部证书／单元检查**：只覆盖明确语义、输入域和检查器保证的部分。
- **完整适配／数学证明**：覆盖精确声明的全部假设、转换、参数、误差与成本。
- **实现及端到端评测证据**：在登记的数据、环境、质量约束与统计方法下支持应用收益；不自动证明未测试场景或生产可靠性。
- **独立模型评审**：帮助发现问题，不替代上述证据，也不等于学术同行评审。

验收时先假定未完成，逐项检查 §2.3，并填写 `ACCEPTANCE.md` 的“声称—领域／理论假设—义务—证明／代码／测试—baseline—指标—独立评审—局限”矩阵。不能因 deadline 临近、剩余预算少、模型都同意、已有漂亮图表或单个候选成功就跳过任何核心项。

原型可暂时粗糙但可持续推进；最终需要运行的产物必须真的存在且复现关键结果。若候选为理论性应用论文，不机械要求生产部署；仍必须证明它解决的是真实领域问题及其新保证。若成功档案要求实验，则不可用理论推导替代尚未完成的必要实验。

只有全部条件成立才按运行器规则标记 complete。有限的负面结论、候选全部暂缓或可投稿草稿未达收益标准，均不得替代正向目标。人类停止与真实阻塞按用户／运行器处理，不伪装成科研成功。

## 11. 记录、检查点与恢复

### 11.1 应用运行与理论材料隔离

每次实际应用研究使用唯一 `applications/<run-id>/`；不同领域／运行不混写。仅有制作协议请求时不要创建假装已启动的运行目录。

| 文件／目录 | 用途 |
|---|---|
| `RUN_CONFIG.json` | 用户领域、授权、资源、来源协议和版本 |
| `STATE.md`、`OPEN-ITEMS.md` | 本运行最新权威状态、有效下一步、句柄、未决义务 |
| `THEORY_CARD.md`、`ADAPTATION.md` | 冻结理论、假设映射、来源 hash、证明缺口 |
| `DOMAIN_MAP.md`、`BASELINES.md` | 域内候选、需求和强基线证据 |
| `APPLICATION_CARD.md` | 当前任务、指标阈值、数据／参数范围及版本 |
| `candidates/`、`archive/` | 候选各版本、搁置／否决理由 |
| `proofs/`、`src/`、`tests/` | 桥接证明、实现、独立检查器 |
| `experiments/`、`artifacts/` | 预登记设计、环境、原始输出、种子、统计分析与复现命令 |
| `review/` | 价值／适配／验证／论文／争议审核快照及调用记录 |
| `PAPER_CASE.md`、`application.md`、`paper/`、`ACCEPTANCE.md` | 论文论证、详细成果、稿件与完成审计 |

应用文件不得覆盖理论项目的 `PREREG.md`、证明、历史 review 或完成状态。原理论的修正以新版本提出并更新依赖关系；原始证据保留。协议只放目标／规则，不追加实验 log。

### 11.2 自动 compact 与恢复

使用实际支持的原生 auto-compaction；在窗口接近上限、下一批可能超限或注意力持续退化时提前保存本运行检查点。依据实际上下文、输出预留与安全余量设置阈值；约 80% 仅为保守参考，不编造当前占用或窗口。

能主动触发时调用真正支持的 `/compact`／工具；在 shell、回复或子 agent 提示词里写 `/compact` 不会压缩主会话。不能主动触发时保存检查点、使用原生压缩／恢复，在安全窗口内继续小批次工作；不得因此宣布 goal 完成。

恢复唯一顺序：

`application_goal.md → 必要的 idea_goal.md 继承条款 → applications/<run-id>/RUN_CONFIG.json → STATE.md → APPLICATION_CARD.md → THEORY_CARD.md / ADAPTATION.md → OPEN-ITEMS.md → 当前证据与任务句柄`。

需要翻译澄清时对照中文版。先确认仍是已授权的应用运行，核验真实进程／工具状态；不从旧摘要推断完成或停机。最高优先级未决项如已过期、已完成或被反例否定，先纠正再执行；不反复将旧“最高优先级”复制到顶部。
